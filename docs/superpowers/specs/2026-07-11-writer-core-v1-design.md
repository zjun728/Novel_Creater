# Novel Creator 写作内核 V1 总体设计

- 日期：2026-07-11
- 状态：用户已于 2026-07-11 正式批准，进入分阶段实施计划
- 唯一代码基线：`4b85e8d`
- 规格分支：`codex/writer-core-v1-design`
- 首个验收项目：`永乐大典 / 典镇山河`

## 1. 目标

Novel Creator 的基础目标是让一部长篇小说持续、连贯、可控地写下去，并始终由作者掌握最终决定权。

V1 的更高目标是产出真正有阅读吸引力的男频长篇：情节丰满、人物群像有变化、对白和情绪有质感、前后事实一致，读者愿意继续读下去。文学价值不是首要指标，故事吸引力、人物可信度和持续阅读欲望优先。

产品不以文学性、华丽文笔、深奥表达、宏大社会议题或“高级感”为成功标准。自然、清楚、顺畅的大白话完全可以获得最高评价。文字的任务是把故事讲明白、把人物写活、让场景和情绪有过程，使读者产生继续看下一章的冲动。

“写得简单”和“写得干”必须严格区分：简单是语言透明、具体、好懂；干是只有事件骨架、结论和资料说明，没有人物欲望、反应、关系、过程、生活细节和后果。V1 必须允许简单，但不能接受干巴巴的骨架、历史材料腔、文献腔、报告腔或设定说明书腔。

首个样板为《典镇山河》，产品定位为：起点/QQ 阅读型男频长篇，架空历史穿越、科技种田/工业经营、群像成长和文明扩张。

V1 验收目标是由作者手动逐章完成并定稿前 30 章，覆盖至少一个自然完成的故事块。自动评分只作辅助，最终是否合格由作者阅读决定。

## 2. 非目标

V1 明确不包含：

- 旧数据库、旧表、旧字段、旧 API 或旧状态兼容。
- 历史章节重开、replacement、Canon 回滚或分支写作。
- 自动连续生成下一章或自动定稿。
- 多用户、登录、角色权限或公网部署。
- 风格/样本资产的审核、上架、运营和 marketplace。
- 对外宣称的全网趋势雷达。现有市场能力只可标记为测试能力，正式趋势系统后续独立设计。
- 用 fake adapter、fixture、报告或 artifact 证明正式产品 Ready。

## 3. 重构策略

采用“保留产品外壳、重构写作内核”。保留经过验证仍有价值的 UI、项目与种子、AI Proxy、Provider 配置、样本资产等；重新建立创作契约、滚动规划、章节生成、原子定稿和 Canon 投影内核。

不在当前脏工作树上继续堆叠修补。后续实施必须从 `4b85e8d` 的干净隔离 worktree 开始；现有未完成 runtime/migration 改动只作参考，不自动继承。

实施时直接删除不符合新设计的旧实现，不保留 dual-write、legacy fallback、兼容字段和旧状态修复分支。

## 4. 核心原则

1. 后端是正式状态的唯一写入口。
2. Canon 是小说已发生事实的唯一事实源。
3. 模型只能生成候选、审核意见和计划建议，不能直接写正式状态。
4. 作者对候选、ChangeSet 和定稿拥有最终决定权。
5. 已定稿正文和已确认 Canon 只向前推进，不回改。
6. 生成阶段负责讲故事，审核阶段负责发现问题，规划阶段负责修正下一次创作输入。
7. 故事块不绑定章节数量，章节只是按阅读容量对连续剧情进行自然切分。
8. 失败必须显式、可恢复且不产生半完成状态。
9. 产品验收必须经过真实产品入口，测试 runner 不能重写产品编排。
10. 先把故事讲得清楚、好看、有血有肉，再谈文学质感、主题深度和语言技巧；后者不能成为生成或验收的硬目标。

## 5. 总体架构

主链如下：

`项目与种子池 -> 本书创作契约 -> 滚动规划 -> 章节创作会话 -> 原稿/工作稿/候选 -> 预定稿审核 -> FinalizationChangeSet -> 作者一次确认 -> 后端原子事务 -> Canon -> 确定性投影 -> 下一章`

写作内核分为五个领域：

### 5.1 创作契约内核

保存渠道、题材、故事发动机、主次风格、内容质量标准、章节目标字数区间、样本与经验选择。所有生成阶段读取同一个正式契约。

### 5.2 滚动规划内核

管理分卷方向、故事块、故事阶段和 SceneTask。长期方向保持粗粒度，当前可写内容保持具体；已执行内容锁定，未来计划可调整。

### 5.3 章节创作内核

每章建立独立 ChapterSession，内部按场景连续生成。工作稿可自由编辑，只有作者明确保存才产生候选。

### 5.4 原子定稿内核

对选定候选只执行一次结构化状态提取，向作者汇总展示全部变化，作者一次确认后由后端单事务提交。

### 5.5 Canon 投影内核

设定、人物当前状态、关系、记忆、弧光和线索都是从 Canon 确定性生成的读取视图，不再独立读取正文或维护第二套事实。

## 6. 数据模型

新 Schema 按以下领域实体重建：

- 项目：`Project`、`Seed`。
- 创作契约：`CreationContract`、`StyleContract`、资产引用。
- 规划：`VolumePlan`、`StoryBlock`、`StoryStage`、`SceneTask`。
- 草稿：`ChapterSession`、`WorkingDraft`、`DraftCandidate`。
- 定稿：`FinalChapter`、`FinalizationChangeSet`、`FinalizationRecord`。
- Canon：`CanonEntity`、`EntityAlias`、`CanonEvent`、`CanonRevision`。
- 投影：`CurrentStateProjection`、`MemoryView`、`ArcProjection`、`PlotThreadProjection`、`ProjectionHead`。
- 语料：`CorpusSource`、`CorpusChapter`、`StyleTemplate`、`ExperienceCard`、参考片段记录。

### 6.1 状态规则

- 章节核心状态只有 `drafting` 和 `final`。
- StoryStage 使用 `pending -> in_progress -> completed`。
- 同一 StoryStage 可以不限次数跨章，不设置 continuation count。
- 未执行的未来阶段可以调整或取消；已被定稿正文依赖的阶段快照不可回改。
- StoryBlock 只有在目标自然完成、失败、明确转向或作者决定结束时关闭。
- 一个章节只能选择一个 DraftCandidate 定稿。
- FinalChapter 一经提交不可修改。

### 6.2 Canon 实体

人物、组织、地点和物品共用 CanonEntity。别名指向稳定实体 ID；别名命中多个实体时必须由作者确认，禁止自动模糊合并。

事实分为：

- 稳定定义，例如身份、出生地、固有规则。
- 动态事件与状态变化，例如受伤、职位变化、关系变化。
- 传闻、误解、主观认知或未证实 claim。

只有“同一 CanonEntity ID、同一稳定字段、两条均为已确认事实、有效时间重叠且命题互斥”才是硬冲突。信息补充、正常演进、关系变化、身份揭示、传闻和误解不算硬冲突。

### 6.3 Revision 一致性

每次定稿产生一个新的 Canon revision。本次定稿产生的正文、Canon 事件、故事块状态和所有投影共享同一 finalization ID 与 revision。

下一章生成前，ProjectionHead 必须等于 Canon head；不一致时阻止生成并从 Canon 重建投影。

## 7. 数据重置与本机边界

清理数据库时：

- 保留“永乐大典”项目、项目基础信息和三个种子：`永乐长明`、`文渊山海`、`典镇山河`。
- 清除旧章节、候选、Canon、设定、人物状态、关系、记忆、弧光、分卷、故事块、节拍、冲突记录和 QA 派生数据。
- 不迁移任何旧派生数据。

首次初始化一次性创建完整 Schema。正常启动不执行大量 DDL。Schema 版本不匹配时拒绝启动，并提示重新初始化开发数据库；V1 不实现旧库迁移。

后端只监听 `127.0.0.1`。当前不设计认证和公网访问；未来服务器部署作为独立安全项目。

## 8. 种子与新书创建

每个项目拥有一个种子池，可以通过 AI 选题问答按需生成种子，也可以手动新增、编辑或删除。系统不强制生成三个种子。

一个项目最终只能存在一个 `selectedSeedId`。只有选定种子可以进入后续创作契约和生成上下文，其他种子仅作为备选。

首章定稿前可以更换选定种子；首章定稿后永久锁定。

选定种子后的创建流程为：

`选定种子 -> 系统提出三个差异化故事发动机方案 -> 作者选择 -> 风格选择 -> 经验方法选择 -> 查看并确认创作契约 -> 自动建立圣经、实体、人物弧光计划、分卷方向和首个故事块`

三层可复用产品能力为：

1. 通用故事质量原则。
2. 渠道/题材 Profile。
3. 可复用故事发动机。

项目专属 CreationContract 由系统根据种子和作者选择自动生成，作者无需每本书手工搭建新架构。

已有定稿章节后修改 CreationContract，只影响下一章及未来内容，不回写历史章节。

## 9. 风格库、样本库与经验库

风格、样本和经验资产在开发阶段统一建设一次，运行时直接推荐、预览、选择和使用，不为每个项目重新搜索或分析语料。

### 9.1 原始语料

本机允许保存小说完整原文、章节结构、来源信息、文件哈希和分析状态。40 多本参考小说可按章节分批交给开发分析模型。

产品区分两层：

- 原始语料层：保存全文和来源证据，可重新分析和追溯。
- 创作资产层：保存风格模板、经验卡、原创微示范和结构化方法。

物理存储采用“本机文件 + 数据库索引”模式：原始文件保存在用户可配置的本机语料目录，不进入 Git；数据库保存来源元数据、文件哈希、规范化章节/片段文本、检索索引、分析版本和生成资产。原文件是来源证据，数据库文本用于检索和分析，两者通过文件哈希校验一致性。

### 9.2 风格模板

每个 StyleTemplate 至少包含：

- 适用题材与预期阅读体验。
- 同一标准场景的完整风格示例。
- 叙事距离、句段节奏和用词密度。
- 对话、潜台词和人物声音。
- 情绪表达和内心活动深度。
- 动作、说明、环境与身体反应的使用倾向。
- 推荐写法、常见风险和原创场景锚点。

系统根据种子和故事发动机推荐三个模板。作者选择一个主风格，可以增加一个次要风味，并记录喜欢或不喜欢的表现，形成完整 StyleContract。

首批资产不按小说数量机械配额，而按写作能力覆盖建设。初始目标为 8 个可明显区分的主风格模板、覆盖情节组织/人物群像/对白/情绪/内心/信息释放/节奏/悬念的 40–60 张高质量经验卡。每个模板必须有同场景示例和至少一个完整应用示例；数量不足时不使用空模板凑数。

### 9.3 正文参考片段

正式写作允许按当前场景检索并注入少量原文片段，参考情节组织、对白节奏、潜台词、情绪、人物刻画和语言节奏。内容相似或局部情节结构相似可以接受，但不得直接复制标志性句子、连续段落、专有名称或高度一致的独特细节组合。

系统保存本次使用的参考来源，并在定稿前对全部语料执行连续文本与高相似片段检查。检测到明显原文重合，或检测服务不可用时，阻止定稿。

初始检测口径为：归一化后出现单段不少于 40 个连续中文字符的相同/近似复制，或同一来源出现三处以上、每处不少于 24 个连续中文字符的独特表达时阻止定稿。语义或情节相似本身只警告，不阻止；阻止必须展示可定位的原文证据，避免把题材惯用表达误判为复制。阈值在真实语料验收中校准，但不能放宽“阻止必须有原文证据”的原则。

## 10. 故事块与章节容量

StoryBlock 是分卷和章节之间的一段连续剧情任务，不是章节容器，也不设置目标章节数。

StoryBlock 保存目标、入场局面、主要压力、涉及人物、未解决项和有顺序的 StoryStage/SceneTask。

章节字数使用项目可配置的目标区间，不再通过“全书总字数除以目标章节数”形成单章硬标准。全书总字数和预计章节数只用于长期规划。

《典镇山河》的初始目标区间采用 3500–4500 个中文字符。低于区间只提示，不阻止作者定稿；接近 4500 字时不再启动新场景，已开始场景可以自然收束到约 5200 字的安全上限。安全上限用于防止失控输出，不要求机械截断句子或场景。

生成接近章节目标区间上限后：

- 不再领取新的 SceneTask。
- 已开始场景可以在自然段落或场景断点停止。
- 当前 Stage/SceneTask 保持 `in_progress`。
- 下一章继续读取同一未完成任务。
- 不要求每章都有钩子、悬念或强反转。
- 不因超字数重新生成整章，不机械切割已经生成的正文。

## 11. 章节创作会话

作者手动点击“生成本章”后建立 ChapterSession。系统不自动生成下一章。

ChapterSession 只读取：

- 当前 CreationContract 和 StyleContract。
- 最新 Canon revision 和相关实体状态。
- 当前卷、active StoryBlock 和未完成 SceneTask。
- 上一章定稿结尾。
- 相关人物弧光和线索状态。
- 当前场景匹配的经验卡与原文参考片段。

### 11.1 小纲与场景计划

场景计划描述当前发生什么、场内人物各自想要什么/担心什么/隐瞒什么、相关事实边界、可用 SceneTask 和自然停止位置。

场景数量、对白轮次、情绪转折、内心字数、身体反应和段落长度都不设固定指标。作者可以确认或编辑整章场景计划后开始生成。

### 11.2 分场景生成

- 一次只生成一个场景，下一场读取本章已生成正文。
- 流式中断只续写当前场景，不重生成整章。
- 场景失败只重试当前场景，不改变模型、风格、参考样本或故事任务。
- 不使用 synthetic/local fallback 冒充生成成功。
- 原始模型输出永久保留。
- 只有确定性排版清理允许自动应用。
- 任何 AI 节奏、风格、情绪或对白修订必须由作者明确触发，并保存为新候选。

### 11.3 工作稿与候选

加载候选后进入一个可变 WorkingDraft。作者可以自由扩写、删减和改写。

- 每次输入只修改 WorkingDraft，不创建候选。
- WorkingDraft 可以自动暂存用于崩溃恢复，但暂存不算候选、不进入 Canon。
- 作者点击“保存为候选”时，才冻结完整正文并建立新的 DraftCandidate。
- 原始 AI 候选不被覆盖。
- 放弃工作稿时可以恢复到来源候选。
- 定稿只能选择已保存候选。

### 11.4 Writer 页面建议布局

Writer 页面采用三个稳定工作区：左侧显示章节、当前 StoryBlock 和未完成 SceneTask；中间为 WorkingDraft 编辑器和字数状态；右侧显示候选版本、参考来源、审核结果和 ChangeSet 入口。默认只展开当前创作所需信息，Canon、设定和诊断通过抽屉查看，避免把后台状态长期铺满写作界面。具体视觉稿在 Writer UI 里程碑开始前单独展示确认。

## 12. 防 AI 味与内容质量

AI 味不是单个句式，而是过度完整、过度功能化、过度解释和过度工整的组合表现，包括功能性对白、统一人物声音、机械冲突轮次、情绪标签、重复身体反应、内心过薄、模板化结尾、段落节奏趋同和泛化场景细节。

正文质量优先级固定为：

1. 故事清楚、具体、顺畅，读者知道发生了什么。
2. 情节、人物、关系、情绪和后果有过程、有血有肉。
3. 长篇事实一致、方向可控、未完成情节能够承接。
4. 风格稳定，机械味和 AI 味不支配阅读体验。
5. 文学质感、象征、主题和社会深度按作品需要自然出现，不主动拔高，也不作为硬指标。

平台不要求模型把普通情节写得诗化、哲学化或充满比喻。大白话只要具体、有场景、有性格、有情绪、有因果，就是合格甚至优秀的正文。相反，辞藻漂亮但像历史材料、编年摘要、档案、报告或设定百科，仍然判定为内容质量失败。

历史实现把大量防 AI 规则放进生成 Prompt，导致模型按指标填充而不是讲故事。V1 使用以下边界：

### 12.1 生成层

生成正文只提供四类信息：

1. 当前发生什么，以及承接哪个未完成情节。
2. 场内人物各自的欲望、顾虑、隐瞒和关系。
3. 本书 StyleContract 与一至两个相关参考片段。
4. 当前事实边界、字数容量和自然停止位置。

生成层不注入：

- 防 AI 味检查表。
- 短句、段落、对白、反差句等数字阈值。
- 固定对白轮次。
- 每场必须完成的情绪转折。
- 一句内心并立即被打断。
- 强制表情、呼吸、喉咙或身体反应。
- 每章钩子或悬念。
- 完整审稿 Rubric。
- 旧项目人物名和剧情专用补丁。

最近章节暴露的问题不转换成新的负面规则。系统通过调整 SceneTask、人物私欲/关系上下文、StyleContract 选择和参考样本来改善下一次生成。

### 12.2 审核层

定稿前保留完整审核：

- AI 味与 StyleContract 偏离。
- 场景丰满度、人物反应、对白潜台词和情绪过程。
- 功能性对白、人物声音趋同和内心活动不足。
- 模板化结尾、身体反应重复和段落节奏机械。
- 信息倾倒、抽象总结和概念空转。
- 时间、地点、知识边界、物品归属和未完成动作。
- 原文重合。

AI 味和一般质量问题只警告，不阻止作者定稿。作者点击修订时才生成独立候选。明显原文复制和真实 Canon 硬冲突必须解决后才能定稿。

作者已认可的定稿章节逐渐成为本项目声音锚点，优先级高于通用防 AI 规则。

## 13. 原子定稿

定稿从已保存候选开始：

1. 作者选择候选并点击定稿。
2. 后端校验候选内容哈希、当前 Canon revision、故事块 revision 和章节状态。
3. 执行原文重合检查。
4. AI 味/一般质量审核可以在此之前独立运行，但不能写状态。
5. 统一提取模型只读取最终正文一次，生成 FinalizationChangeSet。
6. 作者查看、编辑并一次确认全部变化。
7. 后端在一个事务中提交全部结果。

FinalizationChangeSet 包含：

- 章节摘要。
- Canon 事件与正文证据。
- 实体创建、身份揭示和别名确认。
- 人物、地点、物品、组织和关系状态变化。
- 人物弧光实际进度。
- 线索创建、推进、回收或继续悬置。
- StoryStage/SceneTask 完成量和未完成内容。
- 对未来 StoryBlock 或 VolumePlan 的调整建议。

ChangeSet 必须明确区分 `canonChanges` 和 `planSuggestions`。后续设定、记忆、弧光和线索模块不再分别调用模型重读正文。

### 13.1 事务

作者确认后，单事务同时：

- 冻结 FinalChapter。
- 保存 FinalizationRecord 和 CanonRevision。
- 写入 CanonEvent。
- 更新 StoryBlock、StoryStage 和 SceneTask。
- 重建人物、关系、记忆、弧光和线索投影。
- 更新项目当前章节和 ProjectionHead。

任意一步失败全部回滚。幂等键至少绑定项目、章节、候选、候选内容哈希和预期 Canon head；重复请求返回第一次结果，不重复写入。

FinalizationChangeSet 提取失败时不写任何正式状态，可以重试同一提取器或由作者手动补充。Projection 重建失败时事务回滚。

## 14. 定稿后的不可变边界

定稿后正文和当时依赖的规划快照不可修改。不存在旧章节 replacement、重新定稿、Canon 回滚或历史分支。

发现错误时只能：

- 在后续章节中向前纠正。
- 调整尚未执行的未来计划。
- 根本性错误无法前向修正时新建项目。

## 15. Provider 与密钥

浏览器只发送 provider/task 标识、模型选择和普通生成参数。Provider 密钥和真实 base URL 只由后端解析和使用。

任何 Provider 列表、详情、错误响应、诊断、日志和导出均不得包含明文 API key。前端只能看到 `hasKey`、脱敏标识或配置状态。

所有正式生成经过后端 AI Proxy。直接浏览器 adapter 不能成为正式路径。

### 15.1 新项目模型继承规则

新建项目时，默认复制最近一个项目的完整任务模型绑定，包括选题/种子、规划、正文、审核、摘要、提取和润色等任务。复制是新项目创建时的快照；之后修改上一项目不会联动修改已经创建的新项目。

最近项目没有模型配置、某项绑定缺失、绑定模型被禁用或已删除时，该项回退到模型列表中按稳定 UI 排序的第一个启用模型。当前首个默认模型为“联通云 / deepseek-v4-flash”，《典镇山河》初始所有任务均绑定该模型。

如果模型列表没有任何启用模型，AI 操作必须阻止并引导用户配置，不允许静默使用内置模型或 fake adapter。

## 16. 失败处理

- 场景生成中断：保留 WorkingDraft，重试当前场景。
- AI 味/一般质量审核失败：显示“未完成审核”，作者仍可定稿。
- 原文重合检测失败或服务不可用：阻止定稿。
- FinalizationChangeSet 提取失败：不写状态，允许重试或人工补充。
- Canon 硬冲突：阻止定稿，要求修改候选或 ChangeSet。
- 数据库、投影或故事块结算失败：事务完整回滚。
- 不静默切换模型、风格、参考片段或故事任务。
- 不以 fallback 结果冒充正式成功。

## 17. 测试治理

历史 QA 曾把测试 runner 发展成独立 control plane。冻结归档中 45 个 phase-e runner 的 CLI 全部无参数运行，0 个连接正式生产 AI Proxy；测试通过注入 fake provider/apply adapter 构造 happy path。后续 runner、test、JSON 和 report 反复改名，但没有改变验收入口。

V1 必须杜绝 shadow QA。

### 17.1 证据等级

- 单元/fake 测试：只证明函数和协议。
- Disposable DB 集成测试：只证明指定后端事务。
- 固定浏览器回归：只证明已知 UI 路径没有回归。
- 浏览器探索测试：用于发现乱序、中断、刷新和未知 UI 问题。
- 真实 Provider 验收：证明正式 AI Proxy 与 Provider 链路。
- 30 章人工验收：证明产品主流程和内容质量达到目标。

低等级证据不能授予更高等级 Ready。

### 17.2 强制规则

1. 产品验收必须从真实页面的用户入口开始。
2. 写作验收必须经过正式 `UI -> frontend command/store -> AI Proxy/backend service -> transaction -> product DB -> UI result`。
3. 测试可读取 API/DB 进行诊断，但不能使用直接 API 写入替代页面步骤。
4. fake adapter 永远不能授予 Proxy、DB、Live 或 Product Ready。
5. Artifact 只记录证据，不能靠 JSON/Markdown 一致自证成功。
6. 不再创建 e.23/e.24 或按阻断名称递进的 runner。
7. 相同根因再次出现时，停止扩展 runner，回到同一真实产品步骤定位断点。
8. 每个固定浏览器脚本只验证一个用户目标，不建立巨型 runner。
9. 每个里程碑同时执行真实浏览器探索测试。
10. 产品主线程在测试执行前审核入口，执行后审核结果。
11. 正式测试放入统一目录并进入根测试命令；`tmp` 不承载正式验收。
12. 报告必须注明 commit、分支、入口、环境、同次运行证据和证据等级。

### 17.3 测试类型

- 领域单元测试：实体身份、别名歧义、冲突、故事块跨章、SceneTask、WorkingDraft、候选、投影和幂等。
- 后端集成测试：原子定稿、失败回滚、重复提交、revision、Provider 脱敏。
- Prompt 结构测试：生成 Prompt 只能包含允许的四类内容，不含旧项目专名、数字化防 AI 清单或完整 Rubric。
- 前端流程测试：工作稿暂存、显式保存候选、恢复、定稿不可修改和错误恢复。
- 真实浏览器探索：刷新、返回、乱序点击、重复提交、中断、切章、弹窗和错误恢复。
- 真实 Provider 测试：仅在明确人工验收阶段运行。

## 18. 《典镇山河》验收标准

验收表只用于生成后的人工评价和问题定位，禁止把整张评分表、数字阈值或检查清单注入正文生成 Prompt。自动评分只能提供证据，不能代替作者判断。

### 18.1 “愿意继续阅读”的明确含义

“愿意继续阅读”不等于每章必须有悬念、反转或强钩子。阅读牵引力可以来自未完成行动、人物选择的后果、关系变化、阶段答案、新问题、情绪余波、环境变化或对人物命运的关心。

作者读完一章后，应当能够自然说出至少一个具体期待，例如“想看这个选择造成什么后果”“想知道两人的关系怎么变化”“想看主角如何处理已经形成的麻烦”，而不是只能回答“因为结尾又出现了危险”。

阅读牵引力使用 1–5 分：

- 5 分：读完后立即想继续，能够说出两个以上具体期待，并且期待来自人物、关系或因果，不只来自强行悬念。
- 4 分：愿意继续读，至少有一个清楚且具体的期待，对人物选择或局势后果保持兴趣。
- 3 分：可以继续，但没有明显期待；章节基本合格，却容易暂时放下。
- 2 分：阅读中出现明显跳读，感觉情节在执行任务、解释设定或重复既有内容。
- 1 分：不想继续，人物和情节没有形成有效牵引。

即使其他评分很高，只要作者的真实判断是“不想继续读”，该章仍然不通过。

### 18.2 单章内容质量八项评分

每项使用 1–5 分，3 分代表基本可读，4 分代表达到正式样板要求，5 分代表有明显吸引力和辨识度。

验收中的“骨肉丰满”不是要求堆砌描写或灌水，而是正文在事件骨架之外，能够让读者实际经历人物为什么行动、如何犹豫和选择、别人怎样回应、关系如何变化、事情如何发生、代价如何留下。必要的停顿、生活细节、跑题对白和情绪余波属于故事内容，不应被当作无效字数删除。

| 维度 | 5 分表现 | 3 分表现 | 1 分表现 |
|---|---|---|---|
| 情节丰满与因果 | 多个行动、阻力、选择和后果自然咬合；推进中包含关系、信息或代价变化 | 有清楚事件和推进，但层次较单一 | 像任务清单，只完成一个功能点或大量解释 |
| 人物性格与饱满度 | 人物有欲望、顾虑、矛盾、习惯和私人目的；关键选择符合性格又能暴露新侧面 | 人物行为基本一致，但主要服务主线 | 人物是工具人，为了推进剧情突然说话或行动 |
| 对话真实性 | 用词、语气、信息量和回避方式符合身份、经历、关系和当时情绪；角色声音可区分，有潜台词和未说完内容 | 对话通顺且基本符合人物，但部分句子偏功能化 | 所有人声音相同，轮流解释、质问、否认或汇报剧情 |
| 情绪与内心活动 | 情绪有触发、抵抗、变化和余波；内心包含矛盾、记忆、判断或自我欺骗，不只靠身体反应 | 情绪能够理解，但过程和余味较少 | 直接贴情绪标签，或反复依赖脸白、呼吸、喉咙、握拳等反应 |
| 场景与生活质感 | 地点、物件、秩序、利益和生活痕迹参与事件；人物像生活在世界里，而非站在空背景中说剧情 | 场景清楚但较通用，细节主要服务主线 | 场景像舞台空壳，只有对白、动作、结论和设定说明，读感像历史材料或文献摘要 |
| 节奏与信息释放 | 紧张、停留、闲笔和变化自然交替；信息通过行动、证据、误解和关系逐步露出 | 节奏基本顺畅，偶有过快、过慢或解释偏多 | 全章同一速度，连续加压、连续解释或长期空转 |
| 风格稳定与辨识度 | StyleContract 在叙事距离、语言、对白、幽默/严肃比例和情绪深度上清晰可辨，但没有模板化；自然大白话同样可以得 5 分 | 大体符合风格，局部回到通用 AI 文风 | 风格漂移、混杂、刻意追求高级感，或只剩标签，无法看出本书独有声音 |
| 机械味与 AI 味 | 行文有自然不规则性，人物保留沉默、跑题、犹豫和不完美反应；没有一种模板支配全章 | 偶有模板句和功能化表达，但不持续影响阅读 | 过度解释、功能化对白、工整场景、固定钩子、统一人物声音等持续支配全章 |

“情节丰满”不等于事件越多越好。安静章节只要深化了人物、关系、代价、世界生活或未来选择，也可以得到高分；没有意义的冲突、反转和信息堆积不能提高评分。

文学辞藻、复杂比喻、社会议题和哲理表达不单独加分。语言越朴素，只要故事越清楚、人物越鲜活、场景越可感，评分可以越高。整章如果主要由事件概述、背景资料、世界规则、历史沿革和结论构成，即使事实正确、句子通顺，也不能通过内容质量验收。

### 18.3 AI 味与机械味的证据口径

单个短句、单次“不是……而是……”、单个身体反应或某一章安静收束，不能单独判定为 AI 味。只有以下模式持续出现并主导阅读体验时才构成问题：

- 对白几乎每句都承担逼问、解释、反击或推进功能，没有人物自己的节奏和关系语境。
- 动作或对白后紧跟旁白解释其意义，模型不允许读者自行理解。
- 人物情绪反复通过相同身体部位和生理反应表达。
- 每个场景都按“目标、冲突、情绪转折、选择、钩子”的相同顺序完成。
- 每章都用突然来人、脚步声、危险出现、抬头或抽象总结收尾。
- 角色语言趋同，删除名字后无法判断是谁在说话。
- 段落长度、句式、连接词和信息密度长期均匀。
- 场景缺少具体生活、物件和社会关系，只剩抽象压力和任务执行。
- 修订后文字过度平滑，原稿中人物化、偶然性和情绪毛边被抹除。

审核报告必须引用具体原文证据，说明这些模式如何影响读感，不能只给“AI 味较重”这样的结论。

### 18.4 单章硬门禁

以下项目不参与平均分，任何一项失败都不能定稿：

- 不存在真实 Canon 硬冲突。
- 不存在有原文证据的明显复制。
- 候选内容哈希、Canon revision 和 StoryBlock revision 与定稿请求一致。
- FinalizationChangeSet 可完整生成并由作者确认。
- 定稿事务只能完整成功或完整回滚。
- StoryStage/SceneTask 的完成与跨章状态没有丢失。
- 原稿、WorkingDraft 来源和所有已保存候选可追溯。
- API、日志和浏览器不暴露明文密钥、内部调试字段或旧项目人物信息。

### 18.5 多章与故事块验收

单章好看不足以证明长篇系统有效，还必须检查跨章变化：

- 每 3 章回看：不得连续复用相同场景骨架、冲突方式、身体反应或结尾模板；主线、关系、信息或代价至少有一项形成可感知积累。
- 前 10 章回看：核心故事承诺清楚；主角的欲望、选择方式和付出代价能够辨认；核心配角有独立目的，不只是陪衬；至少一条次级关系或线索在发展。
- 每个 StoryBlock 结束时：块目标确实完成、失败或转向；人物和局势留下可见后果；未解决项被准确交给后续，而不是机械清零。
- 前 30 章回看：至少一个 StoryBlock 自然完成；主线局势与开篇相比发生实质变化；人物关系和弧光出现可追踪演进；风格保持稳定；不存在连续多章空转、重复升级或为了留人强造钩子。

### 18.6 V1 通过规则

《典镇山河》前 30 章需要同时满足：

- 所有单章硬门禁通过。
- 前 3 章阅读牵引力平均不低于 4 分。
- 至少 24 章的阅读牵引力达到 4–5 分；其余章节不得低于 3 分。
- 不得连续两章阅读牵引力只有 3 分。
- 八项内容质量在 30 章中的平均分均不低于 3.8 分，且任何单项不得出现 1 分。
- 至少一个 StoryBlock 通过块级验收。
- 真实浏览器主流程完整跑通，状态和正文证据一致。
- 作者完成 30 章阅读后，仍明确愿意继续阅读并继续创作。
- 不得出现连续章节像历史材料、文献摘要、档案报告或设定说明书；发现时即使其他技术指标通过，V1 样板验收仍判定不通过并建议内容层修订。该验收结论不改变“AI 味和一般质量问题只警告、作者仍可自行定稿”的产品权限边界。

过渡章可以得到 3 分，但必须能够说明它在人物、关系、世界生活、代价或后续选择中的必要价值。评分通过但作者不想继续读，V1 判定失败；自动评分失败但作者认为章节有效时，可以记录人工覆盖理由，但不能覆盖 Canon、复制和事务硬门禁。

## 19. 实施里程碑

总体设计在实施阶段拆成独立规格和计划，按依赖顺序推进：

1. 干净 Schema、Canon、实体身份、投影和事务基础。
2. CreationContract、风格库、语料库和经验资产。
3. StoryBlock、StoryStage、SceneTask 和章节容量。
4. ChapterSession、WorkingDraft、DraftCandidate 和编辑器流程。
5. 场景生成、参考检索、防复制检查和质量审核。
6. FinalizationChangeSet 与原子定稿完整闭环。
7. Writer UI 收束、真实浏览器探索和跨层诊断。
8. 《典镇山河》前 30 章人工验收。

每个里程碑单独编写实施规格、计划、测试入口和完成证据。未通过真实产品链验收的里程碑只能标记部分完成。

## 20. 发布与主线

V1 实施从干净 `4b85e8d` 基线建立新分支，不直接合并当前脏 runtime worktree。

每个里程碑必须通过代码审查、领域测试、必要的 DB 集成测试和真实浏览器验收后才能合并。完成 V1 30 章验收后，再确定远端 canonical main/release policy。

旧 `codex/novel-creater-platform-rc`、历史 e.* runner、fixture 和 artifact 不再作为产品主线或 Ready 证据。
