## 1. 问题和复现证据

真实 QA 流程中，第一章正文保存为候选后，抽取模型产生了针对当前章所用故事块、阶段和场景任务的 4 个 `planningPatches`。准备、作者修正及确认均成功，最后提交返回：

```text
HTTP 409
code: FinalizationConflict
message: Finalization state changed; refresh and retry
correlationId: 100e94a9-4cc5-408c-8469-3efc767f9cd4
```

只读复查时，该项目为 0 章定稿，Canon 与 Projection 均为 0 且同步；审查停在 awaiting_author、已确认 R2。没有证据表明已写入部分最终章节或推进事实 head。

精确 QA 项目与会话 ID 记录在项目状态文档。复現无需真实 Provider：用符合当前身份、revision/hash 和正文证据结构的抽取结果，在 `planningPatches` 中引用当前小纲节点即可。测试不得直接写产品数据库模拟成功。

## 2. 根因

| 阶段 | 现有行为 | 缺口 |
| --- | --- | --- |
| prepare／correct | `validate_change_set_context` 核对目标身份、revision/hash、引用和证据区间/hash | 没有核对受保护规划节点集合 |
| confirm | 校验冻结上下文与当前变更集修订，写入确认标记 | 未在确认前检查补丁是否能合法应用 |
| commit | 从历史定稿小纲加当前小纲计算受保护节点；拒绝对应规划补丁 | 保护正确，但发现问题太晚 |
| 确认后处理 | 前端不可编辑；后端 correct/cancel 均要求尚未确认 | 作者无法从已有入口处理被确认但不能提交的变更集 |

代码依据：

- [准备／修正共用校验](../../../backend/services/finalization_checks.py)：`validate_change_set_context`。
- [审查服务](../../../backend/services/finalization.py)：`prepare`、`correct`、`confirm`、`_require_review_state`、`cancel`。
- [原子提交](../../../backend/services/finalization_commit.py)：`_implemented_ids`、`apply_planning_patches`、`commit`。
- [仓储取消围栏](../../../backend/repositories/finalization.py)：`cancel_awaiting_author`。
- [作者审查面板](../../../frontend/src/components/writer/FinalizationPanel.vue)：确认后禁用编辑，补丁只有 replacement 编辑，没有删除或转建议入口。

受保护集合包括历史定稿小纲和当前章小纲引用的 volume、storyBlock、stage、sceneTask。不得把它缩成仅“已完成的场景”，也不得放行值恰好未变化的补丁来绕过现有保护。

## 3. 方案比较

| 方案 | 收益与限制 | 结论 |
| --- | --- | --- |
| 只增强提示词，失败后让作者刷新重试 | 改动少，但模型仍可返回非法补丁；刷新不能解决已确认记录 | 不采用为正式修复 |
| 提前严格拒绝非法补丁，整次准备失败 | 能避免新确认卡死；但合法事实与进度也随之无法呈交作者，重试仍依赖模型 | 可作为最小防御兜底，不单独解决可用性 |
| 确认前把合法但不可执行的补丁转成非权威建议，并统一各阶段校验；另设明确的旧审查恢复动作 | 保留事实、进度和作者知情；恢复需要单独界定核心语义 | 推荐，分 A/B 两个范围审阅与提交 |

禁止的处理方式：修改已确认 payload 或 hash、在 commit 内静默删补丁、放宽历史保护、直接更新数据库状态、把失败回执改成成功、提前开放下一章。

## 4. A：防止新审查再次进入不可提交状态

### 4.1 同一份受保护节点判定

提取纯函数供 prepare、correct、confirm、commit 复用，规则与当前 commit 一致。输入来自服务端读取的历史定稿小纲和当前小纲，不接受前端提交的受保护集合。

prepare 在既有短事务内读取这些依据，并把受保护集合的可验证身份纳入冻结准备上下文。模型调用后，必须重验 authority 与冻结上下文再保存结果；历史小纲缺失、损坏或上下文变化一律拒绝发布。只冻结必要身份，避免把历史正文装入提示词。

本项预计复用已有 JSON 记录，不新建产品库、表或后台流程。实际编码时须验证严格 manifest 契约、大小限制及旧未结束 attempt 的读取边界；若必须升级持久化结构，应另报范围，不能隐式迁移。

### 4.2 只在呈交作者之前转为建议

处理顺序固定：

1. 按现有完整校验验证模型原始 ChangeSet，特别是目标身份、revision/hash、正文证据和全局 ID 唯一性。非法或过期输入不能因“转建议”而获准通过。
2. 对目标属于受保护集合的合法 patch，移出 `planningPatches`，转为已有 `planningSuggestions`。
3. 保留 patch 的 ID、targetId 和 evidence；建议文字明确目标、原字段、建议内容，以及“此项不会修改当前章或历史规划”。不把建议伪装成已执行变更。
4. 保留其他合法未来节点 patch，不改变 `canonEvents` 和 `storyProgressEvents`。
5. 对转换后的完整 ChangeSet 再做严格校验，然后保存 revision/hash，交给作者查看和确认。

字符串和结构化 replacement 均须生成有界、无歧义的建议说明。若转换会超过现有消息长度或集合容量，整次准备失败并保留候选，不能静默截断、丢弃事实或覆盖其他建议。

correct 必须拒绝重新加入受保护目标的可执行 patch；confirm 必须对完整 payload 重新检查可执行性，兼顾已有尚未确认的旧 attempt。commit 保留最后保护，不能因为上游已检查而删掉校验。

对于旧 attempt 缺少新增冻结依据的情况：读取仍应安全显示原记录，不能静默补写 manifest；禁止继续确认，给出明确的重新审查路径。已确认旧 attempt 的处置属于 B。

### 4.3 作者界面和结果

- 当前章事实、实际进度与未来规划建议分区呈现；转为建议的条目说明不会写入规划。
- 作者可在未确认时移除不需要的未来规划补丁，保存为新修订后再确认；不允许直接编辑服务端身份、hash 或受保护集合。
- 被阻止的确认须显示固定、可理解的原因，不泄露内部异常，不仅提示“刷新重试”。
- 本部分只预防新卡死并处理未确认旧审查，**不能宣称恢复了本次已确认 R2 的 QA 记录**。

## 5. B：已确认但未定稿审查的显式恢复

**本项属于 C 类核心语义变化，须单独明确批准；A 不自动授权 B。**

目前已确认 attempt 不能取消，这是现有服务和仓储明确实施的规则。推荐新增职责单一的“撤销本次审查”命令，终止这次尚未提交的审查，保留全部历史确认记录；不是重新打开已定稿正文，也不是清除确认字段后原地编辑。

### 5.1 操作范围和事务围栏

作者先看到说明：“本章尚未定稿。撤销本次审查会保留正文、候选和已有审查记录；重新审查将再次调用模型。”只有作者显式操作才发送命令。

服务端以精确 project/session/attempt/revision/hash 定位，使用与 commit 相容的项目锁及统一锁顺序。在一个事务中核对：

- 项目活动、会话尚未定稿；目标 attempt 仍为当前活动 awaiting_author，且已确认修订与请求完全匹配；
- 不存在该会话的最终章节或定稿回执；不是 committing、committed 或未知提交结果；
- 不修改其他会话或新的活动审查；不要求把已经漂移的旧生成上下文恢复成当前值，旧基线漂移本身不能阻止安全终止未提交审查。

满足条件时仅把目标 attempt 转为 cancelled 并释放活动槽。保留原 payload、全部 revision、确认 revision/hash/时间及候选；不得改正文、Planning、Canon、Projection 和章号。现有表已有 cancelled 状态，Schema 允许终态保留确认字段，但服务层目前禁止；因此不能把“无需改表”误写为“无需批准语义变更”。

若 commit 先成功，恢复必须拒绝撤销并返回已定稿状态；若恢复先成功，旧 commit 必须因 attempt 不再活动而失败。两者不能同时成功。

重复恢复同一精确已取消记录，应幂等返回原结果；丢失响应后允许只读查询确认结果。不能因后来出现新 attempt 而取消新记录，也不能用读取请求触发新的审查。

### 5.2 重新审查

恢复后返回候选选择，由作者再次点击“审查并定稿”，使用新的准备幂等键和当前权威上下文，创建新 attempt。不得自动调用模型、复用旧确认或伪造新确认。每次审查 attempt 仍只做一次结构化提取；旧已取消 attempt 不写 Canon。

本次 QA 记录仅在 B 已批准、实现、测试并通过正式作者入口后恢复；方案阶段不执行数据库修正，也不直接调用恢复写接口。

## 6. 验收条件与验证顺序

先使用现有测试框架和模拟外部 Provider 写最小失败测试，不新增测试平台或长期数据库。

| 组别 | 必须验证的行为 |
| --- | --- |
| A：目标边界 | 历史及当前小纲引用均受保护；未实现未来节点仍可合法修改 |
| A：转换完整性 | 合法受保护 patch 变为可见建议；事实和实际进度保留；非法 ID、过期 hash、坏证据、重复 ID、超容量仍失败 |
| A：生命周期 | prepare 发布、correct 和 confirm 一致；上下文漂移与旧 attempt 不被静默升级；commit 原有保护继续有效 |
| A：作者操作 | 建议与可执行补丁可辨认；删除未来补丁先形成新修订；未保存修改不能确认；失败保留候选 |
| B：恢复守卫 | 仅精确当前已确认未定稿审查可撤销；归档、错误 owner、旧 revision、committing、已定稿均不能越权 |
| B：竞态与幂等 | commit 与恢复最多一个成功；重复与未知结果安全；新 attempt 不受旧请求影响 |
| B：不可变证据 | 旧 payload、revision、确认记录和候选不变；Canon／Projection／Planning／最终章节／下一章不推进 |
| 端到端 | 正式 UI：出现建议 → 作者确认 → 原子定稿；已确认旧审查经显式撤销后可重新审查；不得绕 UI 或直接改表伪装通过 |

顺序：最小 RED → 定向 GREEN → 受影响的 API/服务/前端回归 → 独立审查。数据库事务及竞态使用仓库现有 disposable MySQL 边界；到最终收口再运行适当全量测试、构建和正式浏览器门禁。真实 Provider 验收独立安排，不嵌入自动测试。

A、B 各自独立提交及证据记录。只完成 A 时必须准确报告“新审查预防已完成，已确认旧审查恢复未完成”。当前实现结果及证据分别见 [A 验证](../acceptance/2026-09-05-finalization-preflight-a.md) 和 [B 验证](../acceptance/2026-09-05-finalization-revocation-b.md)。

## 7. 明确不纳入本次方案

- 引用定位的语义准确性、模型质量建议和正文去 AI 味；区间/hash 校验只能证明定位有效，不能证明内容支持结论。
- 小纲篇幅与字段语义、听水设定一致性、规划 AI 范围扩展。
- 推荐服务本身的失败诊断或既有推荐提示分支合并。
- P0-E 连续性页面、P0-F 统一工作台、完整三章创作、千章规模验收。
- 已定稿历史编辑、Canon 回滚、并行章节、后台自动重试、直接数据库清理。

以上均保留为独立待办，不为解决本次阻断扩展实现范围。
