# Novel Creator 选题中心真实市场闭环设计

- 日期：2026-09-04
- 架构基线：`main@b865b57`
- 产品形态：本机单用户、二百万字以上长篇小说创作平台
- 状态：用户已逐节确认，待书面规格复核
- 本轮性质：补齐选题中心真实网络、真实 Provider 和候选种子交接闭环；不实施代码、数据库或 Provider 调用

## 0. 背景与问题

当前选题中心已经具备市场来源、讨论、选题方向、候选种子和创建项目的前后端骨架，但尚未成为可正式使用的完整产品流程：

- 已注册的市场来源均为 `manual_only`，正式界面的“刷新”不能取得实时公开榜单；
- 市场页只强调来源和快照数量，作者不能直接阅读榜单作品明细；
- Topic Center 的八张权威表已经进入代码的 v1.14 schema manifest，但当前正式数据库仍是 v1.13；
- 真实默认 Provider 尚未从正式前端完成“讨论—保存—建项目”验收；
- 现有确定性测试证明了骨架和边界，却不能代替真实产品流程。

本轮目标不是继续增加测试层或搭建第二套选题系统，而是让作者从正式界面完成一次真实、可理解、可追溯的选题流程。

## 1. 目标与成功路径

正式成功路径固定为：

```text
手动刷新公开榜单
→ 查看真实作品明细
→ 自由发起 AI 讨论，或附加市场快照作为依据
→ 显式保存选题方向或候选种子
→ 在候选种子库继续讨论、形成新版本或归档
→ 用指定候选版本创建项目
→ 在项目种子页人工检查、修改并确认
```

市场证据不是讨论的前置条件。作者可以不选择任何榜单，直接输入自己的想法并与 AI 多轮讨论。

完成标准不是“接口存在”或“测试数据可显示”，而是至少五个不同平台真实联网成功，并用应用默认配置的真实模型从前端完成上述路径。

## 2. 方案选择

### 2.1 采用：服务端直连官方公开页面

每个平台拥有一个独立适配器。用户点击“手动刷新”后，后端访问固定的官方公开榜单 URL，校验响应并规范化公开作品元数据，最后写入不可变市场快照。

优点：

- 数据来自平台官方公开页面；
- 不依赖浏览器自动化、登录态或第三方聚合服务；
- 每个平台可以独立失败、独立修复；
- 可以复用现有 `MarketSourceService`、安全传输边界和 `market_snapshots` 权威。

### 2.2 不采用：浏览器自动化抓取

浏览器自动化依赖页面渲染、Cookie 和易变的交互流程，维护成本高，也容易遇到登录和验证码，不适合作为正式数据通道。

### 2.3 不采用：第三方榜单聚合 API

第三方聚合数据的来源、时效和授权边界不透明，并形成新的外部依赖。本轮不引入。

八个适配器是实现候选，不是预先承诺全部可用。每个来源只有在产品主机上完成真实响应、解析和数据质量验证后，才能标记为 `verified_public` 并在界面显示“可刷新”。首版发布硬门槛是至少五个不同平台通过。

## 4. 适配器与数据流

每个平台适配器只负责一个公开页面族：

```text
作者点击手动刷新
→ MarketSourceService 校验来源能力与固定策略
→ 对应平台适配器通过受限 transport 请求官方页面
→ 适配器严格识别页面并提取作品
→ 统一规范化和数据质量校验
→ 写入不可变 MarketSnapshot
→ 市场页展示最新快照及其作品明细
```

所有适配器输出统一作品结构：

- 排名；
- 书名；
- 作者；
- 分类；
- 官方作品链接；
- 页面公开提供时的简介、标签、字数、连载状态和热度指标；
- 来源、抓取时间和适配器版本。

单次快照最多保存 100 条作品，不保存原始 HTML。简介和扩展字段没有公开数据时保持缺失，不推断、不生成。现有 `market_snapshots` 继续作为唯一市场事实库；扩展作品 JSON 结构即可，不新增第二套市场表。

## 5. 网络与内容边界

继续保留现有严格传输约束：

- 只允许清单中精确登记的 HTTPS 域名和页面路径；
- 固定 User-Agent、8 秒超时和 512 KiB 响应上限；
- 拒绝跨域或未批准重定向；
- 不发送登录 Cookie，不调用登录后接口；
- 不绕过验证码、访问控制或反爬挑战；
- 不采集章节正文、评论、用户资料或非榜单页面；
- 页面身份、条目结构或关键字段不符合预期时整次失败。

现有 `checkedAt` 保留为来源策略的审计时间，但不再因超过 30 天而让用户触发的公开榜单刷新自动失效。运行时安全由固定允许列表、包 hash、响应约束和每次严格页面校验共同保证。来源是否继续有效在版本发布与适配器维护时重新验证。

本轮只提供用户手动刷新，不增加定时器、后台调度或自动重试。

## 6. 快照展示与失败处理

市场页需要从“来源状态页”补齐为“市场阅读页”。每个来源必须展示：

- 当前能力：真实刷新或仅人工导入；
- 最近成功时间和本次刷新状态；
- 最新快照作品列表；
- 作品排名、书名、作者、分类、公开指标和官方链接；
- 数据来自网络刷新还是人工导入。

来源之间完全隔离：

- 一个来源失败不回滚其他来源的成功刷新；
- 失败后保留并展示最近一次成功快照；
- 页面明确显示本次失败和固定错误分类，不把旧快照标成刚刚刷新；
- 无法识别的页面不得写入空快照、半成品快照或虚构数据；
- 手动导入继续作为降级入口，但始终标注“人工导入”。

## 7. AI 讨论、方向与候选种子

作者可以从空白讨论开始，也可以为一次讨论附加最多四份市场快照。发送给 Provider 的内容仅包含经过校验的结构化公开元数据，不包含原始 HTML 或小说正文；每份快照只取有界的头部作品，避免把整份市场库塞入上下文。

讨论调用应用当前默认配置的真实 Provider 和模型。Provider 未配置或不可用时：

- 保留作者已输入的内容；
- 明确显示失败原因；
- 提供进入模型设置的入口；
- 不生成假回复、假方向或假种子。

一次成功 AI 回复可以包含普通讨论回复，以及可供作者选择保存的结构化选题方向和候选种子。AI 输出本身不形成正式业务对象，只有作者点击“保存为方向”或“保存为候选种子”后才进入对应权威。

已保存对象继续遵循现有边界：

- 方向和候选种子均有不可变版本；
- 作者可以围绕指定版本继续讨论并形成新版本；
- 候选种子可以归档；
- 指定候选版本可以创建多个相互独立的项目；
- 创建项目时原子复制到现有项目 Seed 权威；
- 项目 Seed 保持待确认，必须在项目种子页人工修改或确认。

不增加自动选题、自动建项目或强制“继续下一步”按钮。

## 8. 数据库策略：现有单库原地升级

后续普通版本升级只维护一个现有正式数据库，不再为每个 schema 版本新建数据库。

本轮直接在当前 `novel_creator_v113` 数据库上从 v1.13 原地升级到 v1.14：

1. 只读预检当前 schema version、manifest hash，并确认八张 Topic Center 表均不存在；
2. 创建一次可恢复备份；
3. 通过明确的离线升级命令执行现有 `19_topics.sql`，新增八张表；
4. 更新 schema metadata 为 `writer-core-v1.14.0` 和当前 manifest hash；
5. 写入或更新必要的市场来源与系统基础包；
6. 验证 99 张 manifest 表、表结构、基础包和应用启动；
7. 任一步失败立即停止，不自动重试；如出现部分 DDL，使用备份恢复。

数据库物理名称本轮保持 `novel_creator_v113`，schema metadata 升级为 v1.14。应用不得在启动时自动执行 DDL，也不得保留兼容两个 schema 的运行时分支。

本轮不迁移、整理或逐项核对旧项目数据，也不删除现有数据。已有项目可以留在库中，但不构成本轮发布验收条件。“典镇山河”以后需要时只复制种子并重新走正式流程。

后续增表、加字段和索引使用显式版本化原地升级命令；真正破坏兼容性的数据重构再单独设计。

## 9. 正式验收

### 9.1 确定性工程验证

- 每个平台适配器使用固定页面 fixture 验证正常、结构漂移、空榜、重复排名、超限和错误链接；
- transport 验证域名、路径、重定向、超时和响应大小限制；
- MarketSourceService 验证来源隔离、最近成功快照保留和人工导入标识；
- Topic Center 服务验证讨论、显式保存、版本、归档和幂等项目交接；
- 前端验证作品明细、中文状态、失败提示、讨论与保存交互；
- 运行相关后端测试、前端单元测试和生产构建。

### 9.2 真实产品验收

在正式应用界面完成且记录以下证据：

1. 至少五个不同官方平台从产品主机真实联网刷新成功；
2. 每个成功来源至少包含 10 条有效作品，书名、作者、排名和官方链接有效；
3. 前端能够查看真实作品明细、来源、抓取时间和公开指标；
4. 一个来源失败时，其他来源和上次成功快照仍可使用；
5. 使用应用默认配置的真实模型完成一次空白 AI 讨论；
6. 再完成一次附加真实市场快照的 AI 讨论；
7. 从 AI 结果显式保存一条方向和一个候选种子；
8. 对候选种子继续讨论并形成新版本；
9. 用指定版本创建项目；
10. 在项目种子页看到待确认内容并由作者手动确认。

最终验收不得使用 fake Provider、虚构榜单、仅调用 API 绕过前端或测试专用页面。

## 10. 实施边界与后续任务

本轮实施包括：

- 单库 v1.13 → v1.14 原地升级命令；
- 八个候选公开榜单适配器及至少五个真实可用来源；
- 市场作品明细界面；
- 真实 Provider 讨论与显式保存闭环；
- 候选版本到项目待确认 Seed 的正式前端验收。

本轮明确不包括：

- 自动刷新、定时任务或无人值守抓取；
- 登录、验证码绕过、正文或评论采集；
- 旧项目数据迁移与清理；
- 新建第二个正式数据库；
- 项目新建表单和项目基本资料编辑；
- Writer Core、Contract、Bible、Planning、Canon、Projection、人物状态、记忆、弧光或章节生成机制调整；
- 为单次功能建设通用爬虫框架、插件系统或第二套市场权威。

“项目新建字段与项目基本资料编辑”作为紧随本轮之后的独立子项目，单独完成设计、计划和实施，避免与真实选题闭环互相扩大范围。

## 11. 设计自检

- 只有一个正式数据库和一个市场事实权威；
- 原地升级是显式离线命令，不是启动时自动迁移；
- 市场来源必须逐个通过真实验证，不能以适配器文件存在冒充可用；
- 至少五来源与真实 Provider 是正式发布门槛；
- AI 可以从用户自由想法开始，不依赖某条市场方向；
- AI 输出不会自动写入方向、种子或项目；
- 项目 Seed 仍由用户手动确认；
- 没有引入自动刷新、正文抓取、浏览器自动化或第三方聚合依赖；
- 没有修改 Writer Core 或恢复第二套项目 Seed 权威；
- 项目资料编辑没有被夹带进本轮范围。
