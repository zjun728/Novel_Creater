## 审核目标

判断该规格能否在不破坏近期 Writer Core 重构成果的前提下，把当前深层创作能力组织成完整作者产品。

重点审核：

1. 是否保持单一当前权威章节、逐章定稿和逐章推进；
2. 是否保持 `FinalizationChangeSet`、原子定稿、Canon 与 Projection 的单一事实源；
3. 是否存在恢复旧链、双 Store、双 API、双页面或第二套人物/记忆/弧光/线索事实源的风险；
4. 全局选题中心、选题方向、候选种子和项目种子的对象所有权是否闭合；
5. “多章浏览、单章生产”的写作工作台是否与现有后端权威一致；
6. 设定库、连续性中心和规划是否正确区分未来意图与已发生事实；
7. 新增后端接口是否能够作为现有核心外围的薄接口实现，是否有需求会迫使修改核心语义；
8. 页面信息结构是否足以摆脱 Demo 感，同时没有过度设计；
9. 上千章按卷导航、历史正文和小纲阅读、当前章编辑是否完整；
10. P0 真实验收是否足以证明三章连续创作、状态传递和作者成果可见性。

## 审核约束

- 必须以该 commit 的真实代码、schema、services、routes 和测试为证据；
- 不要因为这是长篇产品就默认需要多章并行、团队协作或编辑排期；
- 不要建议恢复重构前旧版的写入、定稿或 Canon 链路；
- 可以建议复用旧版的信息密度和三栏任务模型，但不能恢复旧事实源；
- 区分“现有能力只缺前端入口”“需要只读聚合接口”“需要新边界上下文”“会改变创作核心”四种情况；
- 不要给泛泛的行业最佳实践；每项问题必须指出规格章节和代码证据；
- 不实施代码，不生成 PR，不改仓库；只审核规格。
