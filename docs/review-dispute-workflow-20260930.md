# 审稿争议的证据查看与作者处理方案

2026-09-30。状态：用户明确回复“允许”，已批准并实现模型 required 的逐条作者裁决；相关验证与本机 v1.17 增量升级已完成。下文先保留批准前方案，最新实施与验收见文末；确定性校验仍不可绕过。未提交或推送远端。

## 问题与现状

两批真实模型复核已表明：证据引用正确不等于推论正确；再次调用模型也可能否定真实缺陷。见 [诊断记录](review-context-diagnosis-20260929.md)。因此不以额外自动复核作为本方案前置条件。

当前 `ReviewResultsDialog.vue` 展示理由、正文摘录、调整建议，提供定位修改、整章调整及 optional 忽略／恢复。`review_decisions.py` 和 `finalization.py` 只允许忽略 optional；`finalization.py` 确认与 `finalization_commit.py` 提交均拒绝仍含 required 的报告。原报告不可变，作者决定独立保存并参与重写版本校验，备份已有对应处理。

当前 `context_manifest` 保存候选及 Canon／规划／小纲等身份和哈希，不等于完整可展示的历史证据快照。质量报告的正文证据也不等于逐项历史支持证据。不得用最新规划或模型理由冒充当次历史依据，不得把本地 QA 日志当成正式产品的数据来源。

## 推荐交互

入口放在现有审查结果的每条意见内，新增“查看依据／记录异议”，不另建审稿中心。默认仍看原有简洁列表，展开后显示：

1. **模型意见**：原级别、原理由、原修改建议，始终保留；不显示未经证明的“误报已确认”。
2. **本章原文**：完整关联片段及上下段查看、定位到候选全文。正文身份和摘录哈希不匹配时明确失效，禁止写入作者处理。
3. **核对依据**：只读来源、版本、原文，区分“此前已确认事实”“本章正文”“本章小纲／规划要求”。后两者不能显示为已发生的历史。未保存可验证依据的旧报告显示“此报告未保存该项依据”，不自动补造。
4. **作者说明**：选择争议类型（事实归因、前后状态变化、已交代交接、表达偏好、其他），填写理由；可选取确切候选段落或可验证来源片段作为依据。自由说明与可验证引文分开展示。
5. **处理记录**：展示保存时间、作者操作、理由和依据，允许在当前未确认审查撤回自己的处理；撤回新增记录，不抹除历史。

争议类型用于整理，不匹配关键词自动裁决。首次不新增模型调用，不实现全文差异导航或跨库搜索。来源 ID 由程序生成且绑定具体版本；实验中路径加内容的 ID 不能直接当跨修订业务实体身份。

## 操作语义与待决定项

| 意见类别 | 推荐行为 | 对门禁／重写的影响 |
| --- | --- | --- |
| 确定性阻断：版本不符、候选身份／哈希不符、无效事实变更、提交冲突等 | 解释原因并回到对应修复入口 | 永远不能以作者异议跳过 |
| optional | 保留已有忽略／恢复；异议说明可选 | 仅已保存的忽略从重写输入排除，沿用现有规则 |
| suggested | 可记录异议；本批不新增“忽略 suggested”权限 | 记录本身不改变重写输入或定稿条件 |
| 模型 required | 推荐允许作者核对后逐条裁决“保留原稿”，须填写具体理由并选择可验证依据 | **待决定**：已保存且仍有效的裁决可解除这一条模型意见的阻断；其他阻断不变 |

待选择的另一方案：required 也只能记录异议，仍必须修改并重新审稿。它不改变现有规则，但已证实的误报仍可能迫使作者改动原本正确的正文。推荐逐条作者裁决，原因是文学创作的最终内容判断归作者；这属于对现有硬门禁的明确产品调整，不是修复引用代码即可隐含授权。

采用推荐方案时按钮分两步：“记录异议”只保存；“确认保留原稿”再明确说明“此操作仅表示作者不采纳这条模型意见，不表示系统证实无问题”。没有批量全部通过，也不把记录异议自动转成裁决。若原报告还有未处理 required，继续保持阻断；全部可处理项结束后仍须核对事实与进度并执行原正式确认／定稿步骤。

采用推荐方案时，整章按审稿意见调整应排除已被作者有效裁决不采纳的意见，确认页展示排除数；服务端计算有效集合，绑定处理修订，不能前端删标签。全部已不采纳且无剩余意见时不发起空意见重写。记录异议但尚未裁决的意见仍保留。

## 数据与接口边界

- 原报告、severity、理由和报告哈希均不改写。作者说明／裁决另存，绑定 project、session、attempt、candidateHash、reportHash、findingId 与处理修订；不得把 required 裁决塞进现有只准 optional 的 ignoredFindingIds。
- 用追加事件记录说明、裁决和撤回，当前有效状态由这些事件派生。旧记录只读，新审稿或正文／上下文变化后旧决定失效；新报告即使复用 findingId 也不继承。
- 保存时校验当前活动项目／会话、审查未确认未定稿、候选与上下文仍匹配，使用项目锁和修订 CAS。请求绑定幂等标识；响应丢失先重读，旧修订冲突不能覆盖新决定。确认后不允许原地改裁决，应沿已有撤销审查流程重新开始。
- 核对来源由后端在固定上下文中解析，并验证版本／哈希及片段范围，不相信客户端提交的 sourceType。能按不可变版本重建则复用现有数据；不能重建的来源须另存最小原文快照及哈希。编码前核查实际保存能力，禁止只凭 manifest 哈希承诺历史全文随时可读。
- 需要新的作者异议持久化契约及相应迁移，不能只靠 localStorage 留痕；保存的说明／裁决／来源须纳入项目导出导入与身份重映射，定稿历史页只读显示。旧包无记录按空处理，不能产生默认裁决。生产迁移沿用项目备份与升级流程，不在本次设计阶段执行。
- 若批准 required 裁决，在确认、提交、整章调整三个服务端入口复用同一有效意见计算；确定性检查仍独立执行。裁决更改后旧生成引用拒绝，不能让迟到结果覆盖作者的新决定。

## 实施顺序与验收

1. 先完成基于真实保存结构的证据读取与异议记录闭环：界面保存、刷新读回、撤回留痕、过期只读；保持现有确认门禁。
2. required 裁决获明确选择后，再实现可裁决类别、统一有效意见和确认／提交／重写围栏；不自动变更 suggested 的规则。
3. 同批补备份导入导出、定稿只读历史与必要回归，再经隔离页面验证。仅做前端按钮不算完成。

验收至少包括：真实错误保留阻断；required 异议记录本身不放行；批准的逐条裁决只影响目标项；确定性错误始终拒绝；撤回恢复阻断；新候选／新报告不继承；并发保存与定稿不能穿透；生成中修改裁决拒绝旧结果；来源篡改、跨项目引用拒绝；网络失败不伪成功；备份恢复身份／理由／引文和历史只读一致。第九章误归因与第十章真实矛盾用于 UI 和版本测试时，应明确为保存的 QA 案例，不伪称新模型判断通过。

本次交付仅方案与当前状态更新；未修改产品代码、业务数据或模型配置，未调用模型，未提交／推送。待用户选择的仅是 required 的裁决规则，其余界面和存储细节可按上述方案继续细化，无需逐字段审批。

## 批准后的实施与验收

以上“待决定／仅方案”段落是批准前记录，已被本节取代。用户同日明确回复“允许”，授权实现逐条作者裁决。

### 已实现

- 审查结果逐条展开“查看依据／记录异议”。正文、Canon、规划、小纲、契约和圣经按来源区分，作者选择真实来源并引用原句；服务端在当前冻结上下文校验来源、原文及版本，保存所选来源原文快照和哈希。这里只是可核对的来源，不声称模型意见已有充分证据。
- 保存异议不放行；required 的已保存异议有有效依据后，作者另点“确认保留原稿”。该动作保留原报告和原级别，只排除对应的有效意见。撤回追加记录并恢复阻断；旧记录不会抹掉。optional 忽略机制和 suggested 的原权限不变。
- 确认、原子定稿与整章按意见调整共用有效意见计算。只读意见、未保存裁决、跨报告、版本变化、伪造来源和空依据均不能放行；确定性检查独立保留。确认额外绑定作者处理修订，确认后禁止原地更改；确认与撤回以项目事务锁串行化。重写保留原稿并沿用既有处理修订围栏，不向模型传递已被作者裁决不采纳的意见。
- 作者记录保存在 `review_finding_decisions.dispute_events_json`，与原 optional 忽略共享处理修订，独立于不可变报告。记录 note／retain／revoke、理由、类型、引用快照和时间；服务端读取时校验完整记录及状态转换。接口支持相同事件重试，失败时前端保留旧权威状态并要求重读。
- 导出、导入、再次导出保留记录及引用原文，重映射所属意见／报告身份，旧包缺少记录按空处理。定稿审查页面只读展示作者处理历史。仅受限的事件键与内容哈希字段豁免关系 ID 格式，其余包身份、敏感路径校验不放宽；JSON 来源位置使用 `sourcePointer`，不混作文件路径。
