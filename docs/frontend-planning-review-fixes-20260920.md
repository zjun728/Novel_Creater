## 审稿整章调整：明确的能力缺口

本次代码核验：

- `frontend/src/components/writer/FinalizationPanel.vue` 提供当前审稿及 qualityReport.findings，并有候选稿身份、哈希、审稿状态和正文过期保护。
- `frontend/src/views/ChapterWriterView.vue` 已有先保留旧稿再普通生成的保护链，但没有整章审稿意见命令。
- `backend/services/draft_operations.py` 的 StartDraftOperation 校验仅接受 `generate_new` 和局部修改类型；普通生成 author_instruction 上限为 **2000**，局部上限为 **1000**。不能将任意长度意见无损塞入该字段。
- `backend/prompts/chapter_draft.py` 对 `generate_new` 明确不加入当前整章正文，只按已确认小纲等依据生成。源码虽有非 generate_new 分支，现有入口不接受独立的整章 rewrite 命令，不能据这段分支宣称已有可调用整章审稿调整能力。

因此不能可靠通过前端拼接实现原型的完整语义。下一步需要单独确认一个小范围后端契约，而非全面重构：

1. 明确受支持的整章审稿调整命令，由服务端加载对应审稿、原稿及完整有效意见；前端传审稿与候选身份 / 哈希等引用，避免拼接、静默截断。
2. 校验审稿仍对应当前正文和创作依据；正文、小纲、审稿版本变化后拒绝使用旧意见。已定稿、生成中、结果不明状态保持原保护。
3. 复用旧稿保存、操作幂等、停止 / 失败保留和重试机制；旧稿保存失败不得启动调整。
4. 确定作者未保存审稿修正如何处理、哪些有效意见纳入及生成后的重新审稿要求，再接入“基于审稿意见调整”按钮并做真实链路验收。

上述只是缺口和所需契约，不构成本批已实现能力或新增后端授权。
